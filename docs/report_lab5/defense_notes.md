# Шпаргалка до захисту ЛР №5 (локальні дані та керування станом)

> Нумерація 1–33 відновлена за переліком контрольних питань із брифу (теми збережено в тому самому порядку: сховище → стан → Provider → BLoC → списки). Якщо в методичці нумерація інша, відповіді просто переставляються. Файли — відносно кореня репозиторію.

## Локальне сховище (питання 1–6)

**1. Як вибрати тип локального сховища?** За формою й обсягом даних. Кілька простих налаштувань — key–value (SharedPreferences); структурований, зростаючий список — файл JSON або база даних; секрети (токени, ключі) — захищене сховище (Keychain/Keystore). У проєкті: фільтр і сортування — `SharedPrefsSettingsRepository`, каталог закладів — JSON-файл у `LocalPlacesRepository`, секретів застосунок не зберігає. Бази (Hive, Drift) не використано: обсяг малий, а бриф забороняє нові залежності.

**2. Key–value сховище.** Пари «ключ → значення» простих типів, швидкий доступ без схеми. Підходить для налаштувань, прапорців, останнього вибору. Не підходить для масивів об'єктів, пошуку й зв'язків. У проєкті так збережено `filter` і `sort` Home (`<uid>.catalog.filter`).

**3. Файли і бази даних.** Файл (`dart:io`) — найпростіший спосіб зберегти довільний документ; ми серіалізуємо каталог у JSON (`Place.toJson`). База даних дає запити, індекси, транзакції й міграції, але потребує залежності та схеми. Для одного списку, який завжди читається цілком, файл достатній (`lib/data/repositories/local_places_repository.dart`).

**4. Secure storage і чому його не додано.** Це шифроване сховище (iOS Keychain, Android Keystore) для токенів і паролів. JWT чи власних токенів у застосунку немає: сесію сам тримає Firebase Auth і відновлює після перезапуску (`AuthBloc` → `AuthGate`). Зберігати нічого секретного, тому `flutter_secure_storage` зайвий; якби з'явився власний бекенд із токеном, його слід було б додати.

**5. SharedPreferences: призначення, типи, обмеження.** Зберігає `bool`, `int`, `double`, `String`, `List<String>` (на iOS — `NSUserDefaults`, на Android — `SharedPreferences`/DataStore). Обмеження: лише прості типи, немає запитів і зв'язків, усе завантажується в пам'ять, не призначене для великих або критичних даних. Тому масив закладів у ньому не зберігаємо, а лише дві строки налаштувань (`shared_prefs_settings_repository.dart`).

**6. Гарантії SharedPreferences.** Запис асинхронний і не гарантує, що дані потраплять на диск, якщо застосунок убито одразу після `set`. Немає транзакцій і шифрування. Для сортування це припустимо (найгірший наслідок — повернеться попереднє значення); для каталогу ні, тому там атомарний запис: тимчасовий файл + `rename`, записи в черзі (`_write` у `LocalPlacesRepository`).

## Стан у Flutter (питання 7–15)

**7. Ephemeral state та app state.** Ephemeral (локальний) стан стосується одного віджета і не потрібен іншим: поточна вкладка, текст у полях, перемикач «Use custom link», `TextEditingController`. App state спільний для екранів або має пережити екран: каталог, профіль, сесія, налаштування списку. У проєкті перший лишається в `StatefulWidget` (`MainShell._currentIndex`, форми), другий у BLoC (`PlacesBloc`, `ProfileBloc`, `AuthBloc`, `CatalogViewCubit`).

**8. Приклади ephemeral і app state в проєкті.** Ephemeral: `_useCustomLink` та `_preset` в Edit Profile, `_ratings` у `PlaceFormScreen`, пошуковий рядок Favorites. App state: список закладів, обране (Home, Favorites і Details показують одне й те саме), користувач і його провайдери входу. Критерій простий: чи потрібне значення іншому екрану або після закриття цього.

**9. «Lifting State Up».** Коли два віджети залежать від одних даних, стан піднімають до найближчого спільного предка і передають вниз параметрами, а зміни повертають колбеками. У ЛР №3–4 каталог лежав у `MainShell`, і серце на Home одразу бачили Favorites. Недолік: колбеки через кілька рівнів. У ЛР №5 стан піднято ще вище, у `PlacesBloc`, і екрани читають його самі (`PlaceDetailsArgs` має лише `placeId`).

**10. Provider і `ChangeNotifier`.** `ChangeNotifier` — клас зі списком слухачів; метод `notifyListeners()` повідомляє їх про зміну. Модель зберігає дані й логіку, а віджети підписуються й перебудовуються. Це вбудовано у Flutter, Provider лише доставляє його вниз по дереву. У проєкті Provider не використано (бриф: BLoC).

**11. `ChangeNotifierProvider`.** Створює екземпляр `ChangeNotifier` і надає його піддереву, а при видаленні віджета викликає `dispose`. `create: (_) => CartModel()` — модель ліниво створюється один раз. Аналог у BLoC — `BlocProvider(create: …)`, див. `UserScope`.

**12. `Consumer`.** Віджет-будівельник, який підписується на модель і перебудовує лише свою частину: `Consumer<CartModel>(builder: (context, cart, child) => …)`. Параметр `child` дозволяє не перебудовувати незмінні піддерева. Аналог: `BlocBuilder` (з `buildWhen` для тонкого керування) або `context.select`, як у Favorites.

**13. Чому провайдер ставлять «глибоко», а не на кореню.** Щоб стан жив не довше, ніж потрібен, і не перебудовував зайве. Провайдер має бути вище за всі віджети, які його читають, але не вище, ніж треба. У проєкті блоки користувача створює `UserScope` у `MaterialApp.builder`, над `Navigator` (щоб бачили pushed-екрани), а блоки форм — у самих екранах (`LoginScreen` створює `LoginBloc`): вони помирають разом з екраном.

**14. Коли достатньо `setState`.** Для стану одного віджета, який не потрібен іншим: перемикач, поточна вкладка, відкрите меню, контролери форм. Тоді BLoC лише додав би boilerplate. У проєкті `setState` лишився саме там (`MainShell`, `AutovalidateMode` форм, превʼю аватара). Правило: піднімаємо стан, коли його потребує другий екран або він має пережити екран.

**15. Provider проти BLoC.** Provider простіший: мало коду, добре для невеликих моделей. BLoC суворіший: однонаправлений потік подій і станів, чітке розділення UI і логіки, легке тестування (`bloc_test`), історія подій. Обрано BLoC, бо в проєкті вже є `AuthRepository` (ідеальна пара до Repository + BLoC), багато async-операцій і потреба показати події/стани/`BlocListener`.

## BLoC (питання 16–29)

**16. Що таке BLoC.** Business Logic Component: клас, що приймає події, виконує логіку (часто асинхронну, через репозиторій) і видає стани. UI не містить логіки: показує поточний стан і надсилає події. Приклад: `PlacesBloc` (`lib/features/places/bloc/places_bloc.dart`) — завантаження, створення, редагування, видалення закладів.

**17. Event.** Незмінне повідомлення «що сталося»: `PlaceDeleted(id)`, `LoginSubmitted(email, password)`. Події — `sealed`-класи, тож `switch` по них вичерпний. Вони описують намір користувача, а не результат (`places_event.dart`, `login_event.dart`).

**18. State.** Незмінний знімок того, що показати: `PlacesState(status, places, errorMessage)`. Побудований на `Equatable`, тому однакові стани не перебудовують UI, а новий список завжди дає новий стан. Стани входу — `sealed`: `LoginInitial / Loading / Success / Failure / LinkRequired`.

**19. Клас `Bloc` і обробники.** `class PlacesBloc extends Bloc<PlacesEvent, PlacesState>`; у конструкторі `on<PlaceDeleted>(_onDeleted)` реєструє обробник; усередині викликається `emit(newState)`. Початковий стан передається в `super(...)`. Події й стани винесено в `part`-файли поруч із блоком.

**20. Цикл UI → Event → BLoC → State → UI.** Натискання «серця» → `bloc.add(PlaceFavoriteToggled(id))` → обробник зберігає зміну через `PlacesRepository` → `emit(state.copyWith(places: …))` → `BlocBuilder` на Home, Favorites і Details перебудовуються. Потік односпрямований: віджет ніколи не змінює список сам.

**21. Cubit проти Bloc.** Cubit — спрощений блок без подій: методи замість подій, `emit` усередині методів. Менше boilerplate, але немає журналу подій і трансформацій потоку. У проєкті Cubit для простого стану (`CatalogViewCubit.setFilter`, `ChangePasswordCubit.submit`, `ForgotPasswordCubit.sendLink`), Bloc для складного потоку з кількома подіями (`PlacesBloc`, `LoginBloc`, `ProfileBloc`, `AuthBloc`).

**22. `BlocProvider`.** Створює блок і надає його піддереву; закриває його при видаленні віджета. `BlocProvider(create: (_) => LoginBloc(...), child: …)` на екрані входу; `MultiBlocProvider` у `UserScope` для трьох блоків користувача. Читати: `context.read<T>()` (без підписки), `context.watch<T>()` / `BlocBuilder` (з підпискою).

**23. `BlocBuilder`.** Перебудовує віджет при новому стані; `buildWhen` обмежує перебудови. Використано для списку Home (loading / failure / loaded), чипів фільтра (`buildWhen` лише за `filter`), Profile. У `build` не має бути побічних ефектів: лише відображення стану.

**24. `BlocListener`.** Виконує одноразову реакцію на зміну стану й не перебудовує дерево: діалог, навігація, snackbar. Приклади: діалог помилки збереження в `MainShell`, діалог пароля при об'єднанні акаунтів (`LoginLinkListener`), закриття Edit Profile після `saving → idle`, `popUntil` в `AuthGate`. `BlocConsumer` поєднує обидва.

**25. Переваги BLoC.** Розділення UI й логіки; передбачуваний односпрямований потік; блоки тестуються без віджетів (`test/bloc/*`); легко підставити репозиторій-заглушку; стан відтворюваний. Для команди — єдиний шаблон усіх екранів.

**26. Недоліки й boilerplate.** Для простої дії потрібні подія, стан, обробник і файли — багато коду. Тому для простих випадків використано Cubit, а ephemeral state лишено в `setState`. Також кривіша крива навчання, ніж у Provider.

**27. Repository + інтерфейс.** Репозиторій ховає джерело даних за інтерфейсом (`abstract interface class PlacesRepository`), а блок знає лише контракт. Реалізації: `LocalPlacesRepository` (файл), `InMemoryPlacesRepository` (тести й скриншоти). Те саме для `AuthRepository` (Firebase / Fake) і `SettingsRepository`. Заміна сховища не чіпає блоки й екрани.

**28. DI через `RepositoryProvider`.** `MultiRepositoryProvider` у `main.dart` надає `AuthRepository`, `PlacesRepository`, `SettingsRepository`, `AnalyticsService`, `CrashReporter`; їх читають `context.read<T>()` при створенні блоків (`UserScope`). Тести підставляють фейки через `withScope(...)` (`test/helpers/test_harness.dart`). Окремий сервіс-локатор не потрібен.

**29. Async у BLoC і `emit()`.** Обробник може бути `async`: `emit(loading)` → `await repository…` → `emit(loaded)`. `emit` дозволено лише поки обробник не завершився; для потоків — `emit.forEach` (`AuthBloc`, `ProfileBloc`), який сам скасовує підписку. Помилки ловимо `try/catch` і переводимо в стан `failure`, щоб UI їх показав. У `PlacesBloc` зміну спершу зберігаємо, потім публікуємо.

**30. `BlocBuilder` проти `BlocListener`.** Builder повертає віджет і має бути чистою функцією стану; Listener нічого не повертає й призначений для побічних ефектів, виконуваних один раз на зміну. Діалог усередині `build` показувався б при кожній перебудові — це помилка. Для цього й `listenWhen` у `MainShell`: діалог лише коли зʼявилась нова помилка.

## Списки (питання 31–33)

**31. `ListView` проти `ListView.builder`.** `ListView(children: […])` створює всі елементи одразу, підходить для коротких фіксованих списків. `ListView.builder` (і `separated`) створює елементи ліниво, лише видимі, за `itemBuilder` — для довгих чи динамічних списків. Тому каталог Home будується ліниво (`SliverList.separated`); горизонтальні чипи залишилися на `ListView.separated`.

**32. `GridView`: `count`, `builder`, `extent`.** `GridView.count` — фіксована кількість колонок; `GridView.extent` — максимальна ширина плитки, колонки підбираються під ширину екрана; `GridView.builder` — ліниве створення з `SliverGridDelegate`. У дизайні каталог — вертикальні картки, тож `GridView` не вживається: сітка зробила б картки вужчими й змінила б макет Figma. Ми це свідомо описали, а не додали сітку заради вимоги.

**33. `CustomScrollView` і слівери.** `CustomScrollView` об'єднує різні прокручувані частини в один скрол: `SliverToBoxAdapter` — звичайний віджет (заголовок, пошук, чипи), `SliverList` / `SliverGrid` — ліниві списки й сітки, `SliverAppBar` — згортувана шапка. У Home шапка, пошук і чипи — `SliverToBoxAdapter`, картки — `SliverList.separated` (`lib/features/home/screens/home_screen.dart`). `SliverAppBar` не потрібен, бо шапка — власний `AppNavHeader`.

## «Підступні» питання і слабкі місця

- **Чому BLoC, а не Provider?** Бо потрібні явні події/стани й `BlocListener` для побічних ефектів, а `AuthRepository` вже ідеально лягає на Repository + BLoC. Provider було б простішим, це визнана ціна: більше коду.
- **Чому каталог у файлі, а не в SharedPreferences?** SharedPreferences не призначений для масивів вкладених об'єктів, не має гарантій запису; файл JSON дає атомарний запис і ізоляцію по користувачу.
- **Чому не Hive/Drift/SQLite?** Обсяг мізерний і весь список потрібен одразу; бриф забороняє додаткові залежності. Якщо каталог стане великим або з'являться запити по полях, варто перейти на базу.
- **Чому не `flutter_secure_storage`?** Немає секретів: сесію тримає Firebase.
- **Local-first без синхронізації — обмеження.** Дані лише на пристрої; зміна телефона чи видалення застосунку їх втрачає. Cloud Firestore і Storage — наступні роботи. Фото — демо-ассети, а не файли користувача (ЛР №6).
- **Чому `UserScope` над `Navigator`, а не в `AuthGate`?** Pushed-екрани (Details, форма) не є нащадками роута `AuthGate`; блоки, створені там, були б для них недоступні. Це відхилення від брифу (`docs/decisions.md`).
- **Як гарантовано, що каталог не «тече» між акаунтами?** Блоки створюються з `ValueKey(uid)`, а файл каталогу має ім'я `places_<uid>.json` (тест `Switching accounts does not leak…` і `users are isolated…`).
- **Що буде, якщо файл каталогу пошкоджено?** Застосунок не падає: помилка йде в Crashlytics як non-fatal, каталог відновлюється з демо-даних, файл переписується (`storage_test.dart`).
- **Що з повторними натисканнями?** Блоки входу й реєстрації ігнорують подію в стані `Loading`; кнопка показує спінер, поля `readOnly` (тести в `auth_flow_test.dart`, `auth_blocs_test.dart`).
- **Чи є в `build` побічні ефекти?** Ні: діалоги й навігація — у `BlocListener`, аналітика — у блоках.
- **Слабке місце тестів.** Реальні Firebase-вхід через Google/Apple і `requires-recent-login` на справжньому акаунті перевірялись вручну або не перевірялись: автотести працюють із `FakeAuthRepository`.

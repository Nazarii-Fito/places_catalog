# Використання LLM під час розробки (розділ 2 завдання)

## Модель і harness

Для проєктування й верстки використовувалась модель **Claude Opus 5.5** (Anthropic) в агентному середовищі **Claude Code**, розширенні для VS Code. Claude Code працює безпосередньо з локальним репозиторієм: читає й редагує файли, запускає команди `flutter analyze`, `flutter test`, `flutter build ios`, `xcrun simctl` і робить git-коміти. Через протокол MCP (Model Context Protocol) до агента було підключено **сервер Figma MCP**, який дає моделі доступ до макетів ЛР №2. Використано інструменти `get_metadata` (структура сторінки й розміри фреймів), `get_variable_defs` (змінні дизайну), `get_design_context` (структура вузла з точними розмірами, кольорами, шрифтами й посиланнями на ассети), `get_screenshot` (еталонне зображення фрейму) та `use_figma` (домальовування відсутніх екранів Forgot Password і Change Password з наявних шарів макета).

## Робочий процес

Вхідними даними були специфікація вимог із ЛР №2 (функціональні вимоги FR1–FR11, нефункціональні NFR1–NFR7, правила Apple HIG) і посилання на фрейми Figma. Спочатку агент провів розвідку макета: зібрав і дедуплікував токени (кольори, типографіку, відступи, тіні), знайшов розбіжності між екранами та відсутні екрани. За результатами він сформував план, який я затвердив, і поставив питання щодо неоднозначностей. Далі розробка йшла фазами: фундамент проєкту (тема, ассети, моделі, маршрутизація) → перевикористовувані віджети `core/widgets` → екрани по одному → етап 2. Кожен екран після верстки знімався на симуляторі iPhone 17e і порівнювався з рендером фрейму Figma поруч (`docs/compare/`), а позиції елементів вимірювались по пікселях. Розбіжності виправлялись, рішення фіксувались у `docs/decisions.md`. Перед кожним комітом запускались `flutter analyze` і widget-тести, зокрема перевірка відсутності overflow на iPhone SE та 17 Pro Max.

## Приклад запиту до LLM (скорочено)

> Ти — senior Flutter-розробник із досвідом pixel-perfect верстки з Figma. Виконую ЛР №3: створити базову структуру Flutter-застосунку PlacesCatalog і pixel-perfect реалізувати основні екрани за дизайном із ЛР №2 **без бізнес-логіки** (hardcoded/mock-дані, кнопки просто ведуть на наступний екран).
>
> Потрібно зверстати: реєстрацію та авторизацію з відновленням пароля через email; профіль зі зміною пароля; головний екран. Перевикористовувані віджети — у `lib/core/widgets`. Цільова платформа — iOS 14+ за Apple HIG: нижній Tab Bar Home / Favorites / Profile, без Drawer і FAB, свайп назад, деструктивні дії через `CupertinoAlertDialog`, зона натискання ≥ 44 pt, Safe Area.
>
> Обмеження: без state-management бібліотек, Firebase чи HTTP; стан через `StatefulWidget` + `setState`; навігація — `Navigator` з named routes і `CupertinoPageRoute`. Посилання на фрейми Figma: Login — `…?node-id=1-902`, Create Account — `…?node-id=9-24`, Home — `…?node-id=1-70`, Profile — `…?node-id=1-496`.
>
> Робочий процес: спочатку розвідка макета через Figma MCP і план на затвердження (токени, віджети, мапа «екран → віджети», відкриті питання); потім фундамент, віджети й екрани по одному. Кожен екран порівнюй зі скриншотом Figma на тому самому логічному розмірі й комміть окремо.

## ЛР №5 — локальні дані та керування станом (BLoC)

**Інструмент і модель.** Роботу виконано в тому самому агентному середовищі Claude Code (розширення VS Code); моделі Claude 5-го покоління. Вхідні дані — файл `docs/input/lab5_prompt_claude_code.md` з вимогами методички, архітектурою, порядком фаз і критеріями «готово». Figma MCP не використовувався: нових екранів за дизайном не було, а екран Edit Place зверстано в тій самій візуальній мові, що Add Place.

**Процес.** Агент спочатку прочитав код, тести й `docs/decisions.md`, склав план за фазами й поставив три питання (порядок git-комітів; тимчасовий стан між фазами 1 і 3; обсяг BLoC для Forgot Password і Edit Profile). Далі робота йшла фазами з окремим комітом на кожну: (1) слівери Home/Favorites і спільна форма закладу з валідацією; (2) `toJson/fromJson`, `PlacesRepository` (файл і пам'ять), `SettingsRepository`; (3) `PlacesBloc`, `CatalogViewCubit`, `RepositoryProvider` замість `AppScope`; (4) `AuthBloc`, `LoginBloc`, `RegisterBloc`, `ProfileBloc`, Cubit-и паролів; (5) тести, скриншоти й матеріали звіту. Після кожної фази запускались `flutter analyze` (0 зауважень) і `flutter test`; для зміни вигляду екранів агент збирав застосунок на симуляторі iPhone 17 і порівнював скриншоти з попереднім виглядом.

**Що агент зробив самостійно:** написав код, `bloc_test` і widget-тести, зібрав скриншоти (режим `FAKE_AUTH` із параметрами `DEMO_FORM`, `FAKE_LOAD_DELAY_MS`, `FAKE_LOAD_FAIL`), відповіді на контрольні питання й фрагменти коду для звіту (генеруються зі справжніх файлів).

**Де відступив від промпту (і чому).** Блоки користувача створює `UserScope` над `Navigator`, а не `AuthGate`: екрани, відкриті через `Navigator.push`, не є нащадками роута `AuthGate`. Налаштування списку читаються через класичний `SharedPreferences` (мокається через `setMockInitialValues`, як у методичці). Поведінка й причини задокументовані в `docs/decisions.md`.

**Що перевірено вручну, а що ні.** Автоматично: 166 тестів (BLoC, сховище, flow-сценарії, відсутність overflow). Вручну агент перевірив запуск реальної збірки з Firebase на симуляторі (відновлення сеансу й завантаження каталогу з файлу). **Автор перевіряє сам** за чеклістом із `docs/report_lab5/README.md`: проходження сценаріїв на симуляторі й на фізичному пристрої (редагування, перезапуск, зміна акаунта), пошкоджений файл каталогу, вхід через Google/Apple з реальними акаунтами.

**Обмеження LLM, які враховано.** API пакетів (`flutter_bloc`, `shared_preferences`, `bloc_test`) звірялись із встановленими версіями, а не писались із пам'яті; помилки, знайдені тестами (втрата події у `async*`-потоці фейкового репозиторію, дублікати `ValueKey` у тесті), агент виправляв і описував у `decisions.md`.

## ЛР №6 — Firestore, хмарні файли, галерея, мапа

**Інструмент і модель.** Те саме агентне середовище Claude Code (розширення VS Code), моделі Claude 5-го покоління. Вхідні дані: `docs/input/lab6_prompt_claude_code.md` (вимоги методички, ухвалені технічні рішення, доробки за коментарем викладача) і специфікація ЛР №2 (`Фітьо_Лаб2_КПП.docx`), з якої агент відновив таблицю статусів FR. Figma MCP не використовувався: екран вибору локації переведено на справжню мапу за наявним макетом (`docs/screenshots/location_picker.png`).

**Процес.** Спочатку агент прочитав код, конфіги, специфікацію й дизайн, склав план за фазами A–F та поставив два блокуючі питання (хто створює базу Firestore; чи є ключі Supabase). Далі: (A) схема, модель, репозиторій Firestore і правила; (B) `PlacesBloc` на живому потоці, профіль-дзеркало, перемикач бекендів; (C) вибір фото, `PlaceImageView`, `MediaRepository` на Supabase; (D) `CreatePlaceBloc`/`UpdatePlaceBloc` з відкатом; (E) мапа, Nominatim через `dio`, `url_launcher`; (F) тести й матеріали звіту. Кожна фаза — окремий локальний коміт; після неї `flutter analyze` і `flutter test`; після фази B і наприкінці — `flutter build ios --simulator` (перевірка залежностей Swift Package Manager).

**Що агент зробив самостійно:** увесь код і тести (без мережі), скриншоти (звичайна збірка для реальної мапи з тайлами OSM; режим `FAKE_AUTH` для решти), SQL для Supabase, правила Firestore (перевірено на компіляцію `firebase deploy --dry-run`), документи й `manual_steps.md`.

**Де відступив від промпту (і чому).**
- `fake_cloud_firestore` не використано: пакет несумісний з `equatable ^3`; замість нього тонкий шар `PlacesDocumentStore` з in-memory реалізацією.
- `MediaRepository.uploadPlacePhoto` приймає `PlacePhoto.local` замість `File` і повертає `PlacePhoto` замість окремого `UploadedPhoto`; параметра прогресу немає, бо `storage_client` його не дає (UI показує «Uploading 2 of 4»).
- Створено `SupabaseClient` напряму замість `Supabase.initialize` (немає глобального стану й обробки сесій, яких не використовуємо).
- Профільне фото з галереї (необов'язкова частина) пропущено.

**Що перевірено вручну, а що ні.** Агент запускав на симуляторі iPhone 17 звичайну збірку й дивився реальну мапу з тайлами (Location Picker, Place Details) та екрани форми. **Не перевірено ніким:** реальний обмін із Firestore і Supabase (база й проєкт створюються автором за `manual_steps.md`), правила на реальній базі, галерея й камера на пристрої, поведінка без мережі на пристрої, Android. Автор виконує чекліст з `docs/report_lab6/manual_steps.md`, розділ 5.

**Обмеження LLM, які враховано.** Версії й API пакетів (`cloud_firestore`, `image_picker`, `storage_client`, `flutter_map`, `dio`) звірялись із встановленим кодом у `~/.pub-cache`, а не з пам'яті; це виявило, що `SnapshotOptions` Firestore ще не підтримується (серверні мітки в очікуванні дають `null`), що `Supabase.initialize` має застарілий параметр `anonKey` (тепер `publishableKey`), і що `FileOptions` та `StorageException` мають саме ті поля, які використано. Помилки, знайдені тестами (зависання `async*`-потоку при скасуванні; поглинання тапу мапою; `await` на таймері під fake-годинником у тесті), виправлено й описано в `decisions.md`.
